# iOS visual language

The iOS app is a Pathors product and should look like one. Its colour and type
come from the Pathors landing site, not from a neutral iOS default.

**Source of truth:** the `.v2-root` block at the top of `components/v2/v2.css`
in the `landing` repository, plus the font declarations in `landing`'s
`app/layout.js`. When the brand moves, re-sync from there and update this file.

Three files carry it in the app:

| file | what it holds |
| --- | --- |
| `ios/App/Parley/ParleyDesignTokens.swift` | raw hex values, light and dark |
| `ios/App/Parley/Theme.swift` | the adaptive `Color`s views actually use |
| `ios/App/Parley/ParleyTypography.swift` | the type scale, as `Font.parley.*` |

`ParleyDesignTokens.swift` used to carry an "AUTO-GENERATED by
`scripts/generate-design-tokens.mjs`" header. That script and its
`design/tokens.json` input are both gone; the file is hand-maintained and
iOS-only. The desktop app keeps its own palette under `src/` and is not affected
by anything here.

### Shared

| token | value | note |
| --- | --- | --- |
| `brand` | `#1469D4` | `--v2-brand` |
| `sky` | `#2DB6F3` | `--v2-sky` |
| `recording` | `#EF4444` | recording red is a universal signal, and the Pathors palette has no red to replace it with |
| `radius` | `12` | up from `10`; Pathors' cards are softer |

`Theme.brand` and `Theme.sky` are fixed, not appearance-adaptive: they are the
mark's colours and a logo that changes hue with the system theme is not a logo.
`Theme.brandGradient` runs `brand → sky` from `.topLeading` to
`.bottomTrailing`, which is what the landing site puts on headlines, stat
numbers and primary CTAs.

Use `Theme.tintedSurface` for "this is a section" and `Theme.muted` for "this
text is secondary". They happen to be the same blue in light mode; they are
named separately so retuning one doesn't silently drag the other.

## Typography

Two faces, both SIL Open Font License 1.1, both bundled. Neither declares a
Reserved Font Name, so modifying and redistributing them under their own names
is permitted; the licences ship next to the fonts in
`ios/App/Parley/Resources/Fonts/` and are copied into the app bundle.

### DM Sans — the UI face

Everything the user reads: body, labels, headings. Four static weights, taken
byte-for-byte from upstream `github.com/googlefonts/dm-fonts`
(`Sans/fonts/ttf/`):

| file | weight | PostScript name |
| --- | --- | --- |
| `DMSans-Regular.ttf` | 400 | `DMSans-Regular` |
| `DMSans-Medium.ttf` | 500 | `DMSans-Medium` |
| `DMSans-SemiBold.ttf` | 600 | `DMSans-SemiBold` |
| `DMSans-Bold.ttf` | 700 | `DMSans-Bold` |

The same four weights `landing` loads. Statics rather than the
`DMSans[opsz,wght].ttf` variable file because selecting a non-default named
instance of a two-axis variable font is not reliable through
`Font.custom(_:size:)` on iOS; four 78 KB statics are cheaper than debugging
that in the field.

### Alexandria — the wordmark, and nothing else

Alexandria is a display face. At 15pt in a list row it reads as DM Sans with
worse spacing, so **headings stay in DM Sans**. It is used only by
`Font.parley.wordmark` and `Font.parley.displayNumber` (large standalone
numerals — a duration, a count, a stat).

Upstream ships only a variable file, so the two static weights are derived:

```sh
# from google/fonts ofl/alexandria/Alexandria[wght].ttf
fonttools varLib.instancer -o Alexandria-600.ttf 'Alexandria[wght].ttf' \
  wght=600 --update-name-table
fonttools subset Alexandria-600.ttf \
  --unicodes='<latin + latin-ext>' \
  --layout-features+=tnum,lnum,case \
  --name-IDs='*' --glyph-names --recalc-bounds \
  --output-file=Alexandria-SemiBold.ttf
```

and the same at `wght=700` for `Alexandria-Bold.ttf`. The subset drops the
Arabic coverage (332 KB → 54 KB per weight), which is safe precisely because the
face is restricted to a Latin wordmark and digits. `tnum` is kept so
`displayNumber` can use tabular figures and a ticking timer doesn't shuffle its
own digits sideways.

### Chinese falls back to the system face

Neither DM Sans nor Alexandria contains a single CJK glyph, and the app defaults
to Traditional Chinese, so most text on screen is drawn by **PingFang TC** and
only the Latin runs are ours. This is deliberate. CoreText does the substitution
per glyph without being asked, so the helper does not need to sniff the string —
and it must not, because a single mixed line would then have to pick one face
for both scripts.

The metrics survive the mix:

| face | ascent | descent | line box | cap height |
| --- | --- | --- | --- | --- |
| PingFang TC | 1060 | 340 | 1.400 em | 860 |
| DM Sans | 992 | 310 | 1.302 em | 700 |
| Alexandria | 968 | 251 | 1.219 em | 700 |

(per 1000 upm; PingFang read from CoreText on macOS, the others from the shipped
files.)

A line that mixes the two takes the larger box, so a mixed line is exactly as
tall as an all-Chinese line — no ragged leading inside a paragraph. And the gap
between an all-Latin line and a Chinese line is *smaller* with DM Sans (1.302 vs
1.400) than with the system font it replaces (~1.2 vs 1.400), so paragraph
rhythm improves rather than degrades.

What does not match is cap height: Chinese reads a little larger than Latin at
the same point size (860 vs 700). That is equally true of SF Pro, so it is not a
regression — but it is why the scale below is not tuned any smaller.

### The scale

`Font.parley.*`, in `ParleyTypography.swift`. Sizes match the iOS defaults for
the same roles, so swapping `.font(.title3)` for `.font(.parley.title3)` changes
the face and the weight but not the layout. Every role is built with
`Font.custom(_:size:relativeTo:)`, so Dynamic Type still scales it — an app that
ignores Dynamic Type is an accessibility regression and App Review notices.

| role | size | face |
| --- | --- | --- |
| `largeTitle` | 34 | DM Sans Bold |
| `title` | 28 | DM Sans Bold |
| `title2` | 22 | DM Sans SemiBold |
| `title3` | 20 | DM Sans SemiBold |
| `headline` | 17 | DM Sans SemiBold |
| `body` | 17 | DM Sans Regular |
| `bodyEmphasized` | 17 | DM Sans Medium |
| `callout` | 16 | DM Sans Regular |
| `subheadline` | 15 | DM Sans Regular |
| `subheadlineEmphasized` | 15 | DM Sans Medium |
| `footnote` | 13 | DM Sans Regular |
| `caption` | 12 | DM Sans Regular |
| `caption2` | 11 | DM Sans Regular |
| `wordmark` | 22 | Alexandria Bold |
| `displayNumber` | 34 | Alexandria SemiBold, tabular figures |

Call sites use `.font(.parley.body)`. Do not call `Font.custom` in a view; if
the scale is missing a size you need, add a role to `ParleyTypography` rather
than opening the escape hatch twice.

### Registration

The fonts are registered by `UIAppFonts` in the app target's `Info.plist`,
generated from `ios/App/project.yml`. An app target needs nothing else — there
is no `CTFontManagerRegisterFontsForURL` call at launch, and adding one would be
dead weight.

They are deliberately **not** on the `ParleyKeyboard` target. A keyboard
extension runs under a hard memory cap and draws its own minimal UI.

If you add or rename a font file you must touch two places: `resources` (the
file has to land in the bundle) and `UIAppFonts` (the runtime has to be told
about it). `ParleyTypography.unresolvedFaces()` reports any face the runtime
cannot resolve, and the `#Preview`s in `ParleyTypography.swift` show it in a
banner — a green "All 6 faces registered" line means the two lists agree.
